What was built: `operators.js` (10 operators + `fromReplan` + `fromMissed`), `menu.js`, `triggers.js` (12 types, dedupe, escalation, kernel nightly, kv migration), `proposals.js` (propose, accept, reject, expire, revert, safety-direction rule), `api.js` and routes: GET `proposals`, `audit`, `menu`; POST `proposals/accept`, `proposals/reject`, `revert`, `missed`, `feedback`. `store.js` now records the audit row when a change is proposed. `read.js` gained `syncPlan()` (in-place refresh after an accepted change, engine mode only).

Behaviours worth knowing:
- The kernel looks downstream: trimming the 6 Dec long run is refused because it lowers the reference so the 13 Dec long run would break the 110 % rule. The plan as imported is already over the load guard in 29 weeks, so many cut-backs will be refused until the macro regeneration (P4) fixes the plan itself.
- Proposals expire at the end of their first day; accepting a stale one fails with 409 (the plan changed).
- `PLAN_AUTOAPPLY=1` (DEC-1) is off by default; with it, only patches that lower km or intensity apply themselves; moves, swaps and inserted recoveries always ask.

NOT done / blockers before this can go live:
1. DEP-2: login enforcement (`LUMPAD_REQUIRE_USER=1` + proxy) is not confirmed on the live system.
2. Nothing raises triggers automatically from the live sync, check-in or the 11:00/20:00 checks yet; `PLAN_SOURCE` must be `engine` for any change to show in the app (and G3 must have passed).
3. No Home/Day UI for proposals, the menu or the audit list; `ScaleCard` and `MissedSession` still use the old kv flow.
4. Dates are fixed for in-place sync: a version that adds or removes days needs a restart until P4.
5. DEC-1 and DEC-4 (availability input) are unanswered; availability only enters the menu as an `avail` query value.


## Update: no password (athlete's choice, 23 Nov 2026)

The athlete does not want a login for now. Default is unchanged (plan writes return 401 without a proxy-stamped user). **Opt-in switch `PLAN_ALLOW_ANON=1`** accepts callers without a login as `anonymous`. Consequence, stated plainly: while the site is public, anyone who knows the address can accept or reject plan changes, edit goals and availability, and choose daily options, and the audit log cannot tell who did it (events are recorded as `athlete`). The plan engine still blocks any change that breaks the guardrails, and every change can be undone from History. This was already true of the existing public `PUT /api/kv` (check-ins, race results) per the 22 Nov audit (C1/C2).

## Update: shadow mode built (AC-P3-6 clock NOT started)

`server/plan/shadow.js`, opt-in `PLAN_SHADOW=1` (runs after each COROS job): works out what the engine would propose today (gate downgrade) and logs it as an unapplied proposal that expires at the end of the day, raises the nightly kernel-drift trigger, and never accepts anything. `GET /api/plan/shadow` lines each proposal up with what you actually ran. AC-P3-6 needs 14 days of this plus your judgement of the proposals (target ≥ 80 % agreeable); it has not started because nothing has been switched on. Not covered yet: missed-run and check-in triggers still come from the athlete's own taps, not from the live flow.
