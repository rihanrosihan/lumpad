## What the AI Coach can and cannot do (as built)

It is a **selector**, not an author. For the next 8 weeks of a generated season plan the engine builds up to 16 key slots (quality sessions and long runs). Each slot gets at most three **kernel-checked options**, ranked `0.35 purpose + 0.25 personal response + 0.20 context + 0.10 progression + 0.10 variety − penalty`. The model answers with option ids and a ≤ 120-word summary. Then:

- an id that was not offered, a malformed pick, or a pick that would push the week above ~20 % hard km is dropped and **that slot keeps the engine's own best-ranked option**;
- nothing the model returns can add load: every option is rebuilt with no more km than the slot had, and the finished plan goes through the kernel again;
- numbers in the model's text must appear in the evidence it was given, otherwise the text is dropped and the engine's own rationale is stored;
- provider down, monthly cap reached, `PLAN_TOKEN_CAP` reached, junk JSON, or `PLAN_COACH` unset → "engine-only" proposal with the reason recorded. The calls use the existing gateway (`llm.complete`: monthly cap, guard, provider settings) and are logged as `coach_run` rows (`intent plan_macro` / `plan_why`); an identical request is answered from the ledger without a new call.

`PLAN_COACH` is **off by default**. Memory enters scoring only at VALIDATED or MEASURED evidence through a structured `payload.plan_signal`; a hypothesis is shown to the model as context and never scored.
